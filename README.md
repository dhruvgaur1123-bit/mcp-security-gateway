# MCP Agent Security Gateway

A policy-enforcing proxy that sits between an LLM agent (MCP client) and an MCP server over stdio.
It checks every tool call going out and every tool result coming back, so a poisoned document or
a malicious tool description cannot silently steer the agent.

```
 client (agent)  <--stdio-->  [ mcpgw ]  <--stdio-->  MCP server
                                 |
                          policy.yaml + audit.jsonl + FastAPI control plane
```

## What it defends against

| Threat | Where | What the gateway does |
|---|---|---|
| Indirect prompt injection in a tool *result* | server -> client | Scores text with weighted rules; blocks above a threshold and tells the model why |
| Tool poisoning (hidden instructions in tool descriptions) | `tools/list` | Drops the poisoned tool before the agent ever sees it |
| Rug pull (tool definition changes after first use) | `tools/list` | Pins a hash per tool; drops tools whose definition changes |
| Over-broad tool access | client -> server | Default-deny allowlist; explicit `deny` per tool |
| Risky write actions | client -> server | `require_approval`: a human approves each call (fails closed on timeout) |
| PII / secret leakage | both directions | Blocks or redacts emails, phones, SSNs, Luhn-valid cards, AWS/GitHub/Google/`sk-` keys, private keys |
| Obfuscation | all text | NFKC normalisation, zero-width and Unicode-tag-character stripping before matching |

Every decision is written to `audit.jsonl` with the rule that fired.

## Quick start

```bash
pip install -r requirements-dev.txt
python demo/run_demo.py            # same requests with and without the gateway
python -m pytest -q                # unit + end-to-end tests
python eval/run_eval.py            # measured detection results (writes eval/RESULTS.md)
```

Wrap any stdio MCP server:

```bash
python -m mcpgw.cli --policy policy.yaml --audit audit.jsonl --control-port 8765 -- <your server command>
```

In an MCP client config, replace the server's `command`/`args` with the gateway and put the original command after `--`.

### Approvals

With `--control-port`, calls to `require_approval` tools wait for an operator:

```bash
curl localhost:8765/approvals                 # list pending calls
curl -X POST localhost:8765/approvals/<id>/approve   # or /deny
curl localhost:8765/audit?limit=20            # recent decisions
curl localhost:8765/stats
```

Without a control plane, approval-required calls are denied (fail closed).

## Policy

See `policy.yaml`. Unknown tools are denied by default. Per tool you can set `action`
(`allow | deny | require_approval`), `pii_in_args`, and `allow_rules` (e.g. permit an email address
in `send_email` while still blocking SSNs and API keys in the body).

## Measured results

`eval/cases.jsonl` holds 67 labelled cases (generated by `eval/build_cases.py`). Latest run:

| | Result |
|---|---|
| Direct, obfuscated, tool-poisoning, and sensitive-argument attacks | **23 / 23 blocked** |
| Paraphrased / non-English / base64-only attacks | **0 / 6 blocked** |
| False positives on benign calls and results | **3 / 31** |
| PII and secrets redacted in results | **7 / 7** |

Full table and every miss: [`eval/RESULTS.md`](eval/RESULTS.md). A test (`tests/test_eval.py`) fails CI if these numbers regress.

## Limitations (read these)

- Detection is **regex + weights**. It catches known phrasings and common obfuscation, and it
  **misses paraphrased, translated, or encoded instructions** (see the `hard_paraphrased` category).
  Treat it as one layer; the allowlist, approvals, and PII controls do not depend on it.
- It can false-positive on text that *quotes* attack phrases (security tutorials) or code that
  resembles an exfiltration pattern. These are tracked as `benign_hard` cases rather than hidden.
- The evaluation set is small and written by the author, so rates are indicative, not a benchmark.
- stdio transport only; no HTTP/SSE transport yet. Redaction is pattern-based and will not catch names or addresses.

## Ideas for extending it

Add an LLM-based classifier as a second stage for ambiguous scores; HTTP/SSE transport; per-argument
schema constraints (e.g. path allowlists); signed policy files; rate limits per tool.
